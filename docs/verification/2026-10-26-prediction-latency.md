# 联想查询延迟：真实学习库上的 p95 压回 5 ms 以内

日期：2026-10-26。分支 `codex/prediction-ngram`，基于 1.1.34（`e1b5344a`），代码提交 `6454b20e`，版本提交 `c1acfede`，已作为 1.1.35/build123 安装。承接 [1.1.34 记录](2026-10-26-prediction-punctuation-emoji-1134.md)。本轮只改查询实现，联想结果不变。

## 目标与评测

用户要求："接着优化联想查询延迟，把真实学习库上的 p95 压回 5 ms 以内，同样先评测再动手。"

- 快照：用 SQLite 在线备份接口只读复制已安装数据目录中的学习库与各来源库（导入来源 2948 条、历史词对 71991 行、证据 3862 条）到 0700 私有目录；隐私密钥不复制（遗忘表为空，用新随机密钥）；每轮从快照重新复制一份，结束后删除。只输出耗时与结果摘要，不输出任何联想文字。
- 用例：T1 的词边界与句末前文共 4231 个，展示 3 项与准入重查 9 项各跑一遍。评测工具新增 `predictions_sha256`（全部用例的来源与文字摘要），用来核对优化前后结果完全相同。
- 门槛在改动前写入 [`manifest.json`](../../crates/inputia-handy-runtime/tests/fixtures/prediction_eval/manifest.json) 的 `latency_real_learning_copy`：三轮中每个集合的 3 项 p95 ≤ 5 ms；9 项 p95 不高于 1.1.34；联想结果摘要与 1.1.34 相同；公开集各项指标不变；测试与 clippy 通过。
- 1.1.34 基线：3 项 p50 约 4.6 ms、p95 5.5–5.9 ms；9 项 p95 8.5–9.0 ms。中位数就有 4.6 ms，是每次查询的固定开销，不是偶发长尾。

## 耗时来源与改动

临时加分阶段计时（已撤除）后，中位耗时主要在：证据查询 1.69 ms、合并打分 1.45 ms、展示前来源核对 0.67 ms、开库与收尾的隐私检查各约 0.26 ms。逐项核对执行计划后改动如下，均不改变结果：

| 位置                         | 原因                                                                                | 改动                                                               | 单项耗时        |
| ---------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------- |
| 语境拒绝检查（每项一次）     | 优化器选了 `(schema_id, code, created)` 索引，按时间扫描全部空方案证据（3800 多条） | 方案与码形加一元加号，改走 `(origin, normalized)` 索引             | 0.58 → 0.03 ms  |
| 证据查询                     | 遗忘检查写在前文条件之前，每条手动证据（917 条）都要先算一次隐私摘要                | 遗忘检查移到最后，只对命中前文条件的行计算                         | 1.8 → 0.26 ms   |
| 隐私待办检查（开、收各一次） | 每次都重新打开并解析整个集成库                                                      | 按文件身份复用只读连接，与来源库连接同一机制；文件被替换时重新打开 | 0.26 → 0.03 ms  |
| 源库修订读取                 | 连接条件 `CAST(s.id AS TEXT)=v.record_id` 用不上主键，每条记录全表扫描语音库        | 先用 `s.id=v.record_id` 走主键，再保留原来的文本完全相同核对       | 0.76 → 0.013 ms |
| 其他                         | 来源核对与遗忘查询每次重新解析语句                                                  | 改为缓存语句                                                       | 小              |

源库修订读取第一次改成 `s.id=CAST(v.record_id AS INTEGER)` 时，知识库历史的测试夹具（文本主键）有 5 项失败；改为不强制转型的等值条件后，整数主键与文本主键下结果都与原写法一致（含 `0042`、`7.0` 等边界值），测试全部通过。知识库历史引用读取（`knowledge_history.rs`）有同一写法，一并改正。

## 结果

| 集合        | 1.1.34 3 项 p95（三轮） | 优化后 3 项 p95       | 1.1.34 9 项 p95       | 优化后 9 项 p95       |

| T1 开发     | 5525 / 5605 / 5791 µs   | 1171 / 1160 / 1121 µs | 8773 / 8811 / 8983 µs | 1621 / 1661 / 1651 µs |
| T1 测试     | 5563 / 5832 / 5900 µs   | 1165 / 1225 / 1164 µs | 8718 / 8981 / 8834 µs | 1638 / 1630 / 1636 µs |
| T1 开发句末 | 5497 / 5800 / 5849 µs   | 1106 / 1097 / 1115 µs | 8516 / 8799 / 8961 µs | 1734 / 1773 / 1753 µs |
| T1 测试句末 | 5492 / 5871 / 5723 µs   | 1135 / 1151 / 1153 µs | 8561 / 8831 / 8960 µs | 1694 / 1688 / 1738 µs |

- 3 项中位耗时由约 4.6 ms 降到约 0.77 ms。
- 三轮的联想结果摘要都与 1.1.34 相同（`3cb7d6b8…`），稳定性 0 处不一致，评测期间没有触发撤销（导入来源始终 2948 条）。
- 公开集（T1、T2、T5、表情）各项指标与 1.1.34 完全相同。
- `inputia-handy-runtime` 全套 377 项通过；clippy（全目标、`-D warnings`）与格式检查通过。全部门槛通过。
